qodebase

A git platform for many coding agents changing one codebase at once. Built on Cloudflare.

This is qodebase: a git platform for the age of agents. Today one person can start ten or forty coding agents on the same app. qodebase lets them all change one codebase at the same time, without throwing work away, and you follow it from your phone. It is built on Cloudflare.

Here is the problem. Each agent works on its own, on its own copy. Their changes only meet at the end, when they land on main. With a handful of agents that is rare. With twenty, two of them have changed the same file almost every minute. Today the usual answer is: send the later one back, and make the agent start again.

The real problem is order

We replayed Hono's last 346 pull requests in waves of 100, as if each wave were written at once. 48% needed another one to land first. Git reported no conflicts at all.

Before building, we measured. We took the last 346 pull requests of Hono, a popular open-source web framework, and replayed them in waves of a hundred, as if each wave had been written at the same moment. Almost half needed another one to land first. And git reported no conflicts at all. So the hard part is not merge conflicts. It is order.

A collision is redone, not sent back

Every change keeps what it was asked to do. When it collides, qodebase applies that request again on the newest code, tests it, and lands it.

So qodebase lands by intent. Every change carries what it was asked to do, and its review. When Agent 4's change collides with Agent 2's, which landed first, qodebase does not send it back. It applies the same request again on the newest code: by rules for shared files, or by a model for a real conflict. Then the tests run, and it lands. The agent never stops working.

Every change is reviewed, and keeps its record

A reviewer agent reads each change. The request, the verdict, how it landed and the tests stay inside git itself.

$ git log --notes=qodebase -1commit 3f9a2c1 Add a booking formNotes (qodebase): intent Add a booking form to the contact page agent Agent 6 review approved: "the form checks the date" landed redone on the newest code tests passed
Before anything lands, a reviewer agent reads it and gives a verdict. And every change keeps its record: what it was asked to do, who did it, what the reviewer said, how it landed, and the tests. It is stored inside git itself, so it travels with the code. That is why this is not GitHub with agents on top: the unit is a request with its record, and landing is automatic.

Many agents also waste work by building the same thing twice. On qodebase's board, each agent says what it is doing, and one check catches duplicates before work starts. With twenty agents and ten hidden duplicate pairs, no pair was built twice, against eight without the board, and the work finished sooner.

For a fresh app, one strong agent was faster

On the same prompts one Opus agent finished 2 to 4 times sooner than a team, with at least as many features working. Teams pay off for wide work, parallel work and fleets.

Real builds on the same prompts, one run each
We also measured what we did not expect. For a fresh app, one strong agent beat a team: on the same prompts, a single Opus agent finished two to four times sooner, with at least as many features working. So qodebase does not push teams everywhere. Many agents pay off for wide work, for work that must run in parallel, and at fleet scale.

The timeline found the bottleneck

At 40 agents, they waited for a reviewer as long as they worked. Now reviewers scale with the team, and replays run side by side.

Every run has a timeline: each agent's time, working, in review, waiting, merging. In the forty-agent build it showed that agents waited for a reviewer about as long as they worked. So we changed the product: reviewers now scale with the team, and model replays in one train run side by side.

One queue has a ceiling; lanes lift it

2,000 scripted agents for 10 minutes on Cloudflare: eight lanes landed twice as much as one, with a median wait of seconds, and main stayed whole.

At larger scale, one landing queue becomes the limit. So qodebase splits it into lanes, one per area of the code. With two thousand scripted agents for ten minutes on Cloudflare, eight lanes landed twice as many changes as one, the median wait fell from minutes to seconds, and main stayed whole and passing its tests.

Different jobs need different ways to run agents

No one way won everywhere. qodebase keeps the measurements, and picks per job.

A fresh appOne strong agent
A shared task listThe board and a duplicate check
How many agentsA controller that grows the team while landings rise
A port where each step builds on the last (Bun)Land at once, check right after, fix forward
Thousands of agentsLanes by dependency, one door onto main
So the lesson is: different jobs need different ways to run agents. A fresh app wants one strong agent. A shared task list wants the board. Team size wants a controller that grows the team only while landings rise. A port where each step builds on the one before, like Bun's, wants landing at once and fixing forward. And thousands of agents want lanes.
